# CLAUDE.md

Guide for an AI agent or developer changing openaxpp300s. Read the invariants section before touching `device.py`, `protocol.py`, `transport.py`, `state.py` or anything that writes to the serial port. A real supply can be tripped, loudly, by a wrong frame order.

## What this is

openaxpp300s is a GPL-3.0 Python package (commands `openaxpp300s` and `openaxpp300s-mcp`) with a CLI, a Python library and an MCP server for the AX PP300S buck-boost bench power supply (AxinDIY, 0-30 V, 0-10.1 A, 300 W). It talks to the supply over the USB serial port (CH340, 115200 8N1, second Type-C port) using pyserial, without the vendor PC app. It is made for AI agents: every command prints JSON and has a stable exit code, and the MCP server wraps the CLI. The sister projects are open289 (Fluke 287/289 multimeter) and openm454 (oscilloscope), same author, same style; the hardware scripts `tests/hw/bench_289*.py` use open289 as the reference meter.

Hardware status (2026-11-07, three sessions, AX PP300S firmware V1.4.4, Windows 11, CH340, input 19.8 V; in the second and third sessions from a 65 W USB-PD charger):

- Verified on the real supply: port discovery, `status`, `selftest`, `set` of VSET, ISET, OVP, OCP, DELAY, REV, OPP and OTP (all acknowledged), output on and off, VSET accuracy from 0.5 V to 30 V against a Fluke 289 with no load (the setting within 0.1 % + 5 mV at every point), boost to 20/24/30 V from the 20 V input, CV current readback and the CC current limit against the 289 with an electronic load (0.05 to 5 A, about 17.5 W; after the user's front-panel current calibration, in spec at every point), lowering VSET and OVP together with the output on and lowering ISET and OCP together with current flowing (no trip in either case), CV-first versus CC-first priority, DELAY, REV, `watch`, `sequence`, `raw` queries and the refusals, the display colours, the Chinese screen (parameter lists, selection, the ignored Digital VSET and DELAY, cut-off current and cut-off time) and the MCP server against the real supply (every tool except `param_list` and `display_colors`, background jobs included; those two were exercised through their CLI commands only).
- Findings worth knowing: before the user calibrated the supply's current on the front panel (against a recently checked Fluke 289), this unit's CC sat a constant 13.5 mA below ISET (measured at 3 V from 0.1 to 1 A; an uncalibrated unit, not a tool fault); after the calibration the setting is within spec (0.1 % + 5 mA) from 0.05 A to 5 A, and the supply's current readback is within spec from 0.4 A up but noisy at 0.25 A and below; the tool cannot calibrate (no serial command), so if the current is off, calibrate on the front panel and do not compensate in the code; cut-offs on the Chinese screen are silent and the cut-off time compares the on-time accumulated since power-up (or since the last time cut-off), not the time since the last ON; with CV first the switch-on current overshoots ISET by about 60 % at 0.5 A.
- NOT yet verified on hardware: OCP/OPP/OTP trips (only OVP tripped, twice, on the first day), the settings-menu effects, currents above 5 A and powers above about 20 W, the DC5525 power input, CC accuracy at other voltages, the EEPROM writes themselves (the write on a status query is firmware evidence only). Do not describe anything in this group as verified.

CI runs the tests on Windows and Linux against the virtual supply only. Linux was never tried with a real supply.

## Architecture

```
CLI command (cli.py)
  -> device.Supply             validation, limits, safe ordering, readback, settings lock
       -> transport.Session    port lock + open port for one transaction, one frame in flight
            -> pyserial port   or sim.SimSerial
```

- Every transaction opens the port, sends, waits and closes it (`Supply._do` makes a fresh `Session`). Opening a CH340 costs about 1 ms, so nothing keeps the port between frames. This is why a background `log` and a foreground `set` or `off` can share one supply. The port lock (`lock.PortLock`, keyed by port) is held only for the duration of one transaction, with `--lock-wait` (default 5 s) as the wait limit; a holder outside this tool (the vendor PC app, a terminal) gives `BUSY`.
- A change (checks plus all its frames) runs under a second lock, the settings lock (`Supply.changing()`, key `settings_<port>`, re-entrant within one `Supply` object, wait at least 15 s). Without it two processes could each pass the VSET/OVP headroom check and together leave VSET above OVP.
- The supply cannot report its settings. `state/last_sent.json` records every value this tool sent (per port); `status` shows it as `last_sent`, and the safety checks use it for the other half of a pair (VSET sent now, OVP sent last). The front panel can change anything behind the tool's back; `last_sent` is therefore a record, not the truth.
- `state/limits.json` holds the bench limits set by the user (`limits --max-voltage/--max-current/--note`).
- Output contract: `cli.emit` prints one JSON document per line on stdout (`--text` gives a short human form). Errors print `{"ok": false, "cmd": ..., "error": {"code", "message", "hint", ...}}` and exit with `EXIT_CODES[code]`. A failed `set` carries `error.sent` when some frames had already gone out.
- Long loops (`watch`, `log`, `sequence`) register in `state/running/`; `stop` writes a stop request into `state/stop/` that the loop polls every 50 ms (`Stopper`), so the loop ends cleanly (a sequence switches the output off unless `--end keep`).
- `mcp_server.py` never opens a serial port itself. Every tool that talks to the supply runs the CLI in a child process (`Cli.run`) with `OPENAXPP300S_HOME` pinned so server and children share `state/`; `job_status` and `job_stop` only read the job files and write stop requests. Background `log_start` and `sequence_start` are detached children tracked as jobs under `state/mcp_jobs/` (`meta.json`, `stdout.jsonl`, `stderr.txt`), so they survive a server restart and a client disconnect. Because the port is taken per transaction, foreground tools keep working while a job runs.
- Backend choice: `transport.sim_enabled()` is true with `--sim` or `OPENAXPP300S_SIM=1`, and then `resolve_port` returns the port `SIM`. `OPENAXPP300S_NO_SERIAL=1` makes real ports refuse to open. Everything above `Session` is identical for both, so the simulator exercises the real device code.
- Port choice (`resolve_port`): simulator, else `--port`, else `OPENAXPP300S_PORT`, else the port that answered last (`state/port.json`), else `discover()`, which probes USB serial ports (WCH CH34x first, Bluetooth ports skipped) with a status query.

## Invariants that must never break

Safety (the supply trips with a loud alarm that only a front-panel key press clears; unclear values can reach a real load):

1. Never trip a protection on purpose, and never send a sequence of frames that can trip one. The firmware compares OVP with the measured terminal voltage and OCP with the measured current all the time (output on or off), and OPP with the power and OTP with the temperature. The rules in `device.py` are the guard and must stay: OVP at least `max(0.2 V, 1.5 %)` above VSET, checked against the values given now and against the ones sent last (VSET = OVP = 3.00 V tripped on hardware at the step from 2 V); a new OVP/OCP must be above what the terminals show now plus a margin, otherwise it is deferred until the output has come down (and refused when the output is on and nothing in the same call lowers it); OPP above the present power and OTP above the present temperature with margins (5 W, 5 C); OVP never below 0.50 V and OCP never below 0.10 A (an OVP of 0 trips at once and an OCP of 0 after 100 ms, even with the output off).
2. Ranges are enforced here, not by the supply. The firmware range-checks nothing on the serial path: it acknowledges and stores any value, and out-of-range values reach the PWM setpoints. `protocol.REGISTERS` carries the front-panel limits (VSET 0-30.00 V, ISET 0.01-10.10 A, OVP 0.50-30.50 V, OCP 0.10-10.50 A, DELAY and REV 0-9999 s, OPP 10-310 W in 10 W steps, OTP 60-100 C in 10 C steps, list index 0-4). Do not widen them. List-index data of 5 or more is persisted unchecked in the EEPROM and, by the address arithmetic in the firmware, can overwrite the colour data there (FIRMWARE; the effect on the real EEPROM part is INFERRED).
3. Ordering. `Supply._order` sends protections that stay above the output first, setpoints next, and protections that must wait for the output to come down last (`_wait_below`). Raising VSET: OVP first. Lowering VSET and OVP together with the output on: VSET first, wait, then OVP (verified on hardware, no trip). Same for ISET and OCP (verified on hardware in the second session: ISET 1.0 to 0.3 A and OCP 1.5 to 0.6 A with 1 A flowing, ISET first, no trip). Keep `DIGITAL_ORDER` and the early/late/deferred logic intact; tests in `tests/test_cli.py` pin every case.
4. Limits fail closed. If `state/limits.json` exists but cannot be read, `state.get_limits` raises `UNSAFE_OPERATION`; it never falls back to "no limit". Voltage-like values (VSET, OVP, list VSET/OVP) and current-like values (ISET, OCP, list ISET/OCP) above the bench limits are refused. `output on` (while it follows the output, not with `--no-wait`), a list selection with the output on (for 1 s) and every sample of a `sequence` switch the output off again at once if the measured voltage exceeds the voltage limit by more than 2 % + 50 mV, and report `UNSAFE_OPERATION`. The tool never raises the bench limits on its own; only the user does, with `limits`.
5. `raw` is guarded. Without `--unsafe`, documented registers go through the same guarded paths (`apply`, `output`, `select_list`, `set_colors`), so `raw` cannot bypass ranges, limits or the trip checks; undocumented registers are refused. `--unsafe` is for the user's explicit decision only. Keep the guard in the CLI and the MCP schema (the MCP server has no `raw` tool).
6. The simulator wins over ports. With `--sim` or `OPENAXPP300S_SIM=1` the code must never reach a real port, and a conflicting `--port` is `INVALID_ARG`. `OPENAXPP300S_NO_SERIAL=1` must keep refusing real ports in tests.
7. One frame in flight. A `Session` sends the next frame only after the answer or the timeout; after a timeout it pauses and flushes input so a late answer cannot be taken for the next one. The firmware sends the status reply from a timer interrupt; a set-frame sent while a reply is on the wire gets its ACK inserted into the reply. Never pipeline frames, never send a frame while waiting for a query reply, send each 6-byte frame in one write (the parser drops a frame that is not complete 10 ms after its A5).
8. Poll slowly. Every valid frame, status queries included, makes the firmware rewrite the EEPROM field under the front-panel cursor (VSET by default on the Digital/Waveform screens; nothing with the cursor on the DATA box), with no wear levelling and no compare (FIRMWARE). The vendor app's 100 ms polling is about 10 writes per second. Defaults: `watch` and `log` 1 s, fast polling (0.1 s) only while something is expected to change (a VSET step, the soft start). Keep the wear warning in `runner.eeprom_warning` and the advice to select the DATA box on the supply for long logs.
9. After a trip the supply shows nothing but `output_flag` going to 0; byte 11 is meaningless with the output off. Do not invent a trip indicator and do not treat the flag as an alarm state; `status`, `set` and `on` report the possibility in a `note` or `warnings` entry in words. The reverse case is reported too: `status` adds a `note` when the output is on but this tool did not switch it on (the front panel or another program did; the settings in force may differ from `last_sent`). A Chinese-screen cut-off is silent (no alarm; MEASURED), so `on` names it in its `note` when the output flag is still off after its wait. `Supply.output` ("on") judges the output settled when a CV reading sits at the Digital VSET or at the selected list's VSET (each as sent last), or, failing both, when the CV reading is stable 1 s after the soft start; in that last case it adds a note that the voltage is at none of the known setpoints. Keep this: on the Chinese screen the Digital VSET is ignored, so waiting for it alone would report a good output as not applied.

Public API:

10. The JSON output of the CLI and the MCP tool results are a public API, as are the exit codes in `errors.EXIT_CODES` and the error `code` strings. Adding a field is fine. Renaming or removing a field, changing a unit (values are SI: V, A, W, C, s) or reusing an exit code is a breaking change and needs a version bump and a README note. `tests/test_cli.py` and `tests/test_mcp.py` pin the contract. Status fields: `port`, `vout_v`, `iout_a`, `pout_w`, `vin_v`, `temp_c`, `output_on`, `mode` (`CV`, `CC`, `OFF`), `cc_flag`, `output_flag`, `raw`, `latency_ms`, `t`, `last_sent`, `limits` (only when a limit is set), `note` (only when the tool switched the output on and it is off now, or when the output is on and the tool did not switch it on).
11. Exit codes: 0 ok (also a loop ended by `stop`), 1 internal error (`INTERNAL`) or failed self-test, 2 `INVALID_ARG`, 3 `NOT_FOUND`, 4 `BUSY`, 5 `NOT_APPLIED`, 6 `NO_REPLY` / `BAD_REPLY` / `PORT_ERROR`, 7 `UNSAFE_OPERATION`, 130 Ctrl+C outside a loop. Do not change the meaning of the 5/6/7 groups: 5 means the supply acknowledged but showed no effect, 6 means link or protocol failure, 7 means refused for safety, meant to come before anything was sent. Two exceptions today: the bench-voltage guard of invariant 4 reports 7 after it switched the output off again, and `list set N ... --select` sends the list values before the selection check, so a refused selection leaves them sent (the error carries no `error.sent` yet).

Repository hygiene:

12. `Vendor/` (vendor manuals, firmware image, vendor PC app, FlyMcu), `logs/` (raw captures), `re/`, `state/` and `data/` stay untracked and listed in `.gitignore`. Never copy vendor text, images or firmware into a tracked file; describe behaviour in your own words and tag the evidence in `docs/PROTOCOL.md`.
13. No absolute local paths (no drive letters, no user folders) and no real device identifiers in any tracked file, this one and test fixtures included. The CI job `package` greps tracked files for drive-letter paths and fails. Examples use `COMx` or `COM14 (example)`.
14. No emojis in code, docs or commit messages.

## Testing

```
python -m pip install -e ".[test]"
python -m pytest tests -m "not hw" -q
```

- `tests/conftest.py` has an autouse fixture: every test gets a fresh `OPENAXPP300S_HOME` (tmp_path), `OPENAXPP300S_SIM=1`, `OPENAXPP300S_NO_SERIAL=1`, `OPENAXPP300S_SIM_DELAY=0`, no `OPENAXPP300S_PORT`, and a freshly reset simulator state. A test must never reach a real port; do not undo this isolation. If you add an environment variable that changes behaviour, set it in the fixture. Fixtures: `cli` (runs the CLI in process, returns exit code and JSON documents) and `simstate` (read or change the virtual supply). `run_cli_proc` is a plain helper in `conftest.py`, not a fixture (`from conftest import run_cli_proc`): it runs the CLI in a child process, like the MCP server does, and returns exit code, JSON documents and stderr.
- Never run the tool or a test without `--sim` or the isolation on a machine where a real supply is attached.
- The simulator models: the firmware's byte parser (hunt for A5, take 5 bytes, 10 ms timeout, so a stray A5 swallows a frame), the ACK for every valid frame except the query (also for unknown ids and out-of-range data), the status reply on the next 50 ms tick with coalescing, the EEPROM write counter (`eeprom_writes`), soft start (about 1.1 s at about 11 mV, CC flag set meanwhile), the output decay, DELAY and REV, the protections (OVP with step overshoot, OCP, OPP, OTP) with the latching alarm that only a front-panel key press clears (`sim press`), the Digital/Waveform versus Chinese screen behaviour (DELAY and REV ignored on the Chinese screen; the silent cut-offs, with the on-time counter accumulated across ON/OFF and restarted after a time cut-off), CV/CC with a resistive load, and an audit log of the frames received (the last 500 writes). Time can be advanced with `python -m openaxpp300s.sim advance SECONDS`.
- Try the tool by hand without hardware: `python -m openaxpp300s --sim status`, `set -V 5 --ovp 5.5`, `on`, `watch -n 3`, `selftest`. Point `OPENAXPP300S_HOME` at a scratch folder so the state does not mix with real state. Reset the virtual supply with `python -m openaxpp300s.sim reset`; `show`, `set key=value`, `advance`, `press` and `audit` inspect and change it.
- When the hardware shows something new: first record it in `docs/PROTOCOL.md` with its evidence tag, then teach `sim.py` to reproduce it, then add a test that fails without the fix. Anything in `sim.py` that was never observed on hardware stays marked as a guess; keep that honest and never present a guess as verified.
- Hardware tests carry `@pytest.mark.hw` and are excluded by default (`addopts = "-m 'not hw'"`); run them deliberately with `pytest -m hw` with a supply attached. CI never runs them. The marker exists; there are no hw pytest tests yet.
- The hardware harness `tests/hw/bench_289.py` is a script, not a pytest test. It needs the supply on its serial port, nothing but a 10 MOhm meter on the output, and an open289 log running in the background, for example `open289 log --duration 2h --every 0 --format jsonl --out meter.jsonl`. Then run `python tests/hw/bench_289.py --meter-log meter.jsonl --out report.json [--max-voltage 15] [--hold 3]`. It runs one `openaxpp300s` CLI command per step, records its JSON and the wall-clock window in which the output was steady, and compares the meter readings in that window with the supply's own readback and the setpoint. It stays in normal operation (never trips a protection on purpose) and switches the output off at the end, also after a failure. The default `--max-voltage` is 15 V; the second session swept it up to 30 V with no load (the 20 V PD input boosts to 30 V), which needs the user's explicit go-ahead each time: do not raise it without the user.
- The three newer hardware scripts are also scripts, not pytest tests, and follow the same rules (normal operation only, output off at the end). `bench_289_cc.py` and `bench_289_cc_cvload.py` need an electronic load, the 289 in the A jack in series with it and an open289 log for the reference (`--meter-log`): use the e-load in constant-voltage mode below VSET for anything that needs CC (constant-resistance mode oscillates against the supply's CC loop; `bench_289_cc.py` runs in CR mode and shows this), and keep OCP well above ISET when testing CV-first priority (its switch-on overshoot is about 60 %). `bench_289_cc_cvload.py` sets the priority back to CC first at the end. `bench_chinese.py` needs the supply on the Chinese screen and a load that draws almost nothing below 3 V; it uses no meter. Run each with `--help` first and never without the user's go-ahead on the real supply.
- CI matrix: Windows and Linux, Python 3.10, 3.12 and 3.14, plus a package job (path grep, build, `twine check --strict`, wheel smoke test against the virtual supply). Keep the code at Python 3.10 compatibility.

## Protocol reference and open questions

`docs/PROTOCOL.md` is the reference (the Chinese edition is `docs/PROTOCOL.zh-CN.md`; keep both in step). Every protocol claim carries an evidence tag: FIRMWARE (seen in the disassembly of V1.4.4, with the address), MEASURED (on the hardware), VENDOR (vendor PDF or vendor PC app) or INFERRED. Change a claim only with new evidence and update the tag. Do not paste firmware text or vendor text into it.

Facts worth knowing before changing code (details and addresses are in the reference; the tags say where each fact comes from):

- Frame `A5 ID lo hi sum 5A`; every valid frame except ID `0xFF` gets a single `01` byte; `0xFF` gets a 15-byte reply (Vout mV, Iout mA, Pout 10 mW, Vin 10 mV, temperature 0.1 C, byte 11 CC flag, byte 12 effective output flag). The supply never transmits unsolicited, so everything is polling. (FIRMWARE and MEASURED; the Vin and temperature units are INFERRED from readings and thresholds.)
- The reply is sent from the 50 ms timer tick (FIRMWARE; measured 15-55 ms, median about 48 ms); the ACK arrives about 12-14 ms after the frame (MEASURED, USB latency). Vout/Iout/Pout refresh every 100 ms and are frozen while the on-device settings menu is open (FIRMWARE).
- Byte 12 is the effective output state, not the commanded one; it goes to 0 on DELAY, the REV off-phase, any protection trip, a Chinese-screen cut-off, a front-panel OFF and entering the settings menu (FIRMWARE; DELAY, REV, an OVP trip and both Chinese-screen cut-offs also MEASURED). A trip cannot be told apart from those. Byte 11 is meaningful only with the output on (FIRMWARE and MEASURED); under load it read 0 in CV and 1 in CC (MEASURED, second session).
- A remote ON re-enables the output after a trip (FIRMWARE; MEASURED after an OVP trip). No serial command clears or reads the alarm (FIRMWARE).
- Settings sent over serial survive a power cycle only if their field is the one under the front-panel cursor when a frame arrives (VSET by default on the Digital/Waveform screens); OPP, OTP and CC-first persist only when the settings menu is left on the supply; the output state is never persisted; colours are always persisted (21 EEPROM bytes, about 210 ms). (FIRMWARE; not checked across a power cycle on hardware.)
- The supply's front-panel-only state (interface, flip, key beep, current filter, calibration, statistics) has no serial command (FIRMWARE).

Open questions (see the open-questions section of the reference):

- What ADC channel 9 senses (byte 11) and why it reads 1 with the output off.
- Whether the output-enable gates (the ADC channel 7 condition, and the Chinese-screen edit on cursor 6) can hold the output off while byte 12 reads 1.
- What a VSET or ISET above the range does to the PWM (saturate or wrap). Do not test; the tool refuses such values.
- The EEPROM part size and the real wear budget (about 72k writes per hour to one cell at 20 Hz in the worst case). By the firmware the status query sets the save flag too (the flag is stored before the ID is dispatched); not observed on hardware, it needs a probe on the EEPROM's I2C lines.
- The exact HSE frequency and MCU part (RAM above 48 KB is used, so it is not a genuine STM32F103RC).
- The worst-case query latency with a key held on the supply.
- The role of the discharge pin and what happens when ON is sent while the settings menu is open.
- Everything in the "not yet verified" group in the hardware status above.

Moved out of the open questions (now verified on hardware, second session): the Chinese screen (lists, selection, cut-offs), CV/CC priority, the display colours, the MCP server against the real supply, voltages above 15 V (no load), loaded operation up to 1 A and byte 11 under load; third session: CC verified up to 5 A and about 17.5 W after the user's current calibration (the earlier 13.5 mA offset was the unit's uncalibrated current, now in spec). Still open: OCP/OPP/OTP trips and the rest of the "not yet verified" group.

## Release process

1. Make sure CI is green on main and `docs/PROTOCOL.md`, the README, `skills/openaxpp300s/SKILL.md` and the MCP `INSTRUCTIONS` match the code. Hardware re-testing after the review fixes was done in the second session; the README must still list what remains unverified (the "NOT yet verified" group in the hardware status: OCP/OPP/OTP trips, the settings menu, currents above 5 A and powers above about 20 W, the DC5525 input, CC accuracy at other voltages, the EEPROM writes).
2. Bump `__version__` in `openaxpp300s/__init__.py` (the only place; `pyproject.toml` reads it dynamically).
3. Commit, then tag `vX.Y.Z` equal to the version and push the tag: `git tag vX.Y.Z && git push origin vX.Y.Z`.
4. `release.yml` runs: `checks` (the full CI workflow) -> `build` (fails if the tag differs from `__version__`; builds sdist and wheel; `twine check --strict`) -> `github-release` (creates the GitHub release with the artifacts and generated notes) -> `pypi` (trusted publishing, no token, environment `pypi`).
