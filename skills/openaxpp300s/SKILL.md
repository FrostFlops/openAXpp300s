# AX PP300S bench power supply -- `openaxpp300s` (CLI + MCP server, GPL-3.0)

Python package that talks to an AX PP300S through its second Type-C port ("TypeC serial", a CH340 USB-serial bridge, 115200 8N1). Written for AI agents: every command prints JSON. Protocol and internals: `docs/PROTOCOL.md` in the repository. Do not reverse-engineer again; read it if you need to change the code. The supply sends nothing on its own and cannot report its settings, so this tool polls and keeps a record of what it sent.

Run it (the working directory does not matter for an installed package):
- installed (`pip install openaxpp300s`): `openaxpp300s <cmd>` and the MCP server `openaxpp300s-mcp` (register: `claude mcp add -s user openaxpp300s -- openaxpp300s-mcp`; give the full path of `openaxpp300s-mcp` if pip's Scripts folder is not on PATH);
- from a checkout: `python -m openaxpp300s <cmd>`; PowerShell `.\openaxpp300s.cmd <cmd>`; Bash `./openaxpp300s.sh <cmd>`.

Every command prints JSON on stdout. One-shot commands print ONE object; `watch`, `log` and `sequence` print one object per line (samples or events) and end with `"event": "done"` and a summary. `--text` (global option) prints a human-readable form; use JSON when you parse. Global options work before or after the command: `-p/--port COMx`, `--sim` (virtual supply), `--lock-wait S` (wait for another command using the port, default 5), `--timeout S` (per answer, default 0.3), `--retries N` (default 2), `--verbose` (every frame on stderr).
Errors: `{"ok": false, "cmd": ..., "error": {"code", "message", "hint"}}` with a non-zero exit code. Exit codes: 0 ok (also a clean stop), 1 internal error or self-test failed, 2 bad argument, 3 not found, 4 port busy, 5 not applied, 6 no reply / bad reply / port error, 7 refused as unsafe. Read `error.hint`: it says what to do. Durations are `30s`, `5m`, `1.5h` or `forever`.

## Before you start
- Plug the supply in by its serial Type-C port (the data port, not the power input) and switch it on. `openaxpp300s ports` lists the serial ports and `ports --probe` asks each USB one for a PP300S status; the port that answers is remembered for later commands. No `--port` is needed when only one supply is attached.
- Close the vendor PC app and any terminal on that port: the port is held by one program at a time (`BUSY`, exit 4). The vendor app also polls every 100 ms, which wears the supply's EEPROM (see EEPROM wear).
- Ask the user what is connected to the output and what the limits are (maximum voltage and current the load can take). Do not guess. Check `openaxpp300s limits` first: if the user already recorded bench limits and a note, use them. If not, ask, then record the answer with `limits --max-voltage V --max-current A --note "what is connected"`. Settings above the limits are refused. Never raise the limits without the user's OK.
- First command in a session: `openaxpp300s status` (or `selftest`). With nothing plugged in you get `NOT_FOUND`.
- Hardware status (verified on 2026-11-07 in three sessions, AX PP300S firmware V1.4.4, Windows 11, CH340, input 19.8 V, in the second and third sessions from a 65 W USB-PD charger): port discovery, status, selftest, setting VSET/ISET/OVP/OCP/DELAY/REV/OPP/OTP, output on/off, VSET accuracy 0.5-30 V against a Fluke 289 with no load (the setting within spec, 0.1 % + 5 mV, at every point), current readback and the current limit (CC) against the 289 with an electronic load from 0.05 A up to 5 A (about 17.5 W), after the user calibrated the supply's current on the front panel, lowering ISET and OCP together with current flowing (no trip), CV/CC priority, DELAY, REV, watch, sequence, raw queries, the refusals, the display colours, the Chinese screen (parameter lists, selection, cut-off current and time) and the MCP server against the real supply (every tool except `param_list` and `display_colors`, whose CLI commands were verified). NOT verified on hardware yet: OCP/OPP/OTP trips (only OVP tripped, twice, on the first day), the settings menu, currents above 5 A and powers above about 20 W, the DC5525 power input, CC accuracy at other voltages, the EEPROM writes themselves. Treat those as untested and tell the user so when you use them. What this skill says about the EEPROM writes, persistence over a power cycle, the settings menu and the trip logic comes from the firmware analysis in `docs/PROTOCOL.md`, not from hardware tests.

## Two ways to drive the supply
Use the MCP tools when they are available in the session (tools named `status`, `set`, `output` ... from the `openaxpp300s` server); use the CLI via Bash for everything else. Each MCP tool that talks to the supply runs the CLI in a child process (open the port, work, release per transaction), so validation, limits, ordering and the error codes are the same.

| MCP tool | CLI | notes |
|---|---|---|
| `status` | `status` | measured output, input voltage, temperature, mode, output flag, `last_sent`, `limits` (when set) |
| `set` | `set` | `voltage`, `current`, `ovp`, `ocp`, `delay`, `rev`, `opp`, `otp`, `priority`, `wait`; safe order, refusals |
| `output` | `on` / `off` | `on` (boolean), `wait`, `wait_timeout`; follows the output until up or down |
| `param_list` | `list select` / `list set` | Chinese-screen parameter lists 0..4: voltage, current, OVP, OCP, cut-off current and time, `select` |
| `display_colors` | `color set` / `color reset` | Digital-screen colours (`#RRGGBB`, `0xRGB565` or a name) |
| `watch` | `watch --quiet` | samples for `seconds` (default 5) or `count`, returns statistics and the last sample |
| `log_start` / `job_status` / `job_stop` | `log` / (job output) / `stop` | background log to CSV or JSONL |
| `sequence_start` / `job_status` / `job_stop` | `sequence` / (job output) / `stop` | background timed voltage/current steps |
| `selftest` | `selftest` | read-only health check |
| `ports` | `ports --probe` | find the supply |

Notes:
- `status`, `set`, `output`, `param_list`, `display_colors`, `watch`, `selftest` and `ports` take `max_wall` (seconds); a call that runs past it returns `TIMEOUT` (a change may have been sent: read `status`). The port is taken per transaction, so foreground tools keep working while a background log or sequence runs.
- Background jobs live in the openaxpp300s state folder (`state/mcp_jobs/`), keep running if the client disconnects, and another client's server using the same state folder can see and stop them. `sequence_start` checks the steps with a dry run before it starts the job. Follow with `job_status`, end with `job_stop` (a sequence then switches the output off unless it was started with `end: keep`).
- No MCP tool, use the CLI: `limits` (show or change the bench limits, deliberately not an agent tool), `color list` (the colour elements, their defaults and what was sent last), `registers` (the register table with ids and ranges), `raw` (one frame; guarded, see Safety), `running` (list running watch/log/sequence commands, MCP jobs included), `stop`. The parameter-list values this tool sent show up in `last_sent` of `status`; the supply cannot report them.

## Choosing commands
- What is the supply doing now: `status`. One query, about 50 ms. Shows the output flag, mode, the measured values and what this tool sent last.
- Set a voltage and current limit: `set -V 5 -I 1 --ovp 5.5 --ocp 1.5`. Give the protections in the same call; the tool sends them in a safe order and, with the output on, waits until the output follows the new VSET (`settled`).
- Switch on: `on` (waits for the voltage to come up: about 1.1 s soft start plus settling, about 1.4 s on hardware and 1.7 s into a constant-current load, plus any DELAY or REV; with DELAY or REV above 20 s it returns after the frame with `settled: false` and a note). Switch off: `off` (waits until it is down). `--no-wait` returns after the frame and one status.
- A few seconds of statistics (min, max, mean, Ah, Wh): `watch --for 30s --every 1 --quiet`, or `watch -n 20` for samples.
- A long record to a file: `log --duration 1h --every 1 --out run.csv` (CSV columns `pc_time,local_time,vout_v,iout_a,pout_w,vin_v,temp_c,mode,output_on,ah,wh,step`; `--format jsonl` for JSONL). Run long logs in the background (Bash `run_in_background`, or MCP `log_start`) and end them with `openaxpp300s stop` (or `job_stop`). Tell the user the file path.
- Timed steps: `sequence --steps "5,1,10; 9,1,20"` or a vendor CSV (`voltage,current,seconds`, an optional header). Each step sets VSET and ISET only, so set an OVP above the highest step first (`set --ovp ...`); a step without OVP headroom over the OVP sent last is refused. `--repeat N` (0 = until `stop`), `--end off|keep`, `--log FILE`, `--dry-run` checks the steps against the ranges, the bench limits and the OVP sent last, and sends nothing. Use `--dry-run` first.
- Chinese-screen parameter lists (only if the supply shows the Chinese screen; verified on hardware): `list set N --voltage ... [--select]`, `list select N`. The tool sends the list values first and the selection last. `list select` is refused before anything is sent when the list's OVP is below the voltage at the terminals now (it would trip); raise that list's OVP first. VSET/ISET/OVP/OCP/DELAY/REV frames act only on the Digital/Waveform screens (firmware analysis; verified for VSET and DELAY: on the Chinese screen a VSET is ignored and `set` with the output on reports `NOT_APPLIED` after 3 s, and DELAY is ignored, the output comes on at once); the screen is chosen on the supply, not over serial. Changing the selected list's voltage with the output on moves the output at once. By the firmware analysis (not tried across a power cycle), a list value sent over serial is saved only if it belongs to the selected list and the supply's cursor sits on that field; with the cursor on the list number (the default on the Chinese screen) the values live in RAM only and are lost at power-off, and the selection itself is saved.
- On the Chinese screen `on` accepts the selected list's VSET (as sent last) as the expected voltage. If the output settles at neither the Digital VSET nor the list's VSET, `on` still returns once the reading is stable, with a `note` saying so: check which screen is active and what the list holds before going on.
- Cut-offs (Chinese screen): a cut-off current or cut-off time switches the output off by itself. It is SILENT, no beep, unlike a protection trip. The cut-off current acts after the current has stayed under the threshold for a few seconds (about 5.5 to 6 s seen with about 0 A flowing). The cut-off time compares the on-time ACCUMULATED since power-up (or since the last time cut-off or statistics clear), not the time since the last `on`: a short cut-off time can cut the output at once after `on`. After a time cut-off the counter restarts. When `on` does not settle, its `note` names a cut-off as a possible cause. If the output went off with no beep, suspect a cut-off, tell the user, and do not send `on` again until the cut-off settings are known.
- Display colours (verified): `color list`, `color set vout=#FFE000`, `color reset`.

## Interpreting values
- Values are SI units: volts, amperes, watts, degrees Celsius, seconds. `vout_v` is the measured terminal voltage, `iout_a` the measured current, `pout_w` the measured power, `vin_v` the input voltage (the supply's own DC input), `temp_c` the supply's internal temperature (the value OTP compares).
- `mode`: `CV` (constant voltage), `CC` (constant current: the load pulls the current limit, the voltage is below VSET) or `OFF`. `mode` is OFF whenever the output flag is 0. `cc_flag` is the raw byte 11: it reads 1 for about a second after the output switches on (soft start) and is not meaningful while the output is off. Trust it only with the output on and settled.
- `output_flag` (`output_on`) is the effective output state, not the command. It is 0 during DELAY, in the REV off-phase, after any protection trip, after a cut-off on the Chinese screen, after a front-panel OFF, and after entering the supply's settings menu. A trip shows ONLY as this flag falling to 0 without a command from you; it cannot be told apart from the others, and the supply cannot say which protection fired. `status` adds a `note` when this tool switched the output on and it is off now; `on` adds a `note` when the flag is still 0 after its wait; `set` adds a warning when the output was on before and is off after. Conversely, `status` adds a `note` when the output is ON but this tool did not switch it on: the front panel (the user pressed the output key) or another program did, and the settings in force may differ from `last_sent`. If you see it, tell the user, and read `status` (voltage, current, mode) before changing anything; do not assume the values you sent earlier are what the output is running on.
- `last_sent`: the values this tool sent last (value, raw, time), by key (`voltage`, `current`, `ovp`, `ocp`, `delay`, `rev`, `opp`, `otp`, `priority`, `output`, list and colour keys). The supply cannot report its settings and the front panel may have changed them, so `last_sent` is a record of what was sent, not what is in force. After a power cycle or a front-panel change, read `vout_v` instead of trusting it. Values are rounded to 10 mV and 10 mA; `sent[].value` says what was really sent.
- `set` results: `sent[]` (key, name, value, unit, raw, id, `ack` `01`, `latency_ms`, `attempts` when a frame was resent, in the order sent), `output_on_before`, `status`, `settled` and `settle_s` with the output on and a new VSET, and `warnings[]` (for example OVP unknown to this tool, OCP not above ISET). Read the warnings and pass them on.
- `watch` samples and `log` rows carry `t` (PC epoch seconds; `pc_time` in the CSV) and `vout_v`, `iout_a`, `pout_w`, `vin_v`, `temp_c`, `mode`, `output_on`; log rows add the running `ah` and `wh`. The summary has `samples`, `ah`, `wh` (integrated by the tool from the samples while the output is on, not read from the supply), `on_s`, `modes`, `stats` (min, max, mean) and `stopped_by` (`count`, `duration`, `stop`, `link_lost`, `interrupt`; a sequence also `output_off`, `error`, `end`).
- Accuracy measured against a Fluke 289 (no load, two sessions): the meter reads 1.7 to 7 mV above VSET between 0.5 V and 30 V, and the supply's own readback sits about 0.4 to 4 mV below the meter (8.5 to 8.6 mV at 0.5 V, where the mean included settling). The setting is within spec (0.1 % + 5 mV) at every point; the readback too, except that 0.5 V mean. The readback is good enough to confirm a setting, not to calibrate a meter. Current readback at 0.5 A in CV was 0.3 mA above and 1.9 mA below the 289 in two runs; for the current readback in CC see the next point.
- Current limit of this unit: before the user calibrated the supply's current on the front panel (against a recently checked Fluke 289), the real current in CC at 3 V (an e-load in constant-voltage mode) was about 13.5 mA BELOW ISET at every setting tried (0.1 to 1 A), outside the vendor spec (0.1 % + 5 mA). After the calibration the setting is within spec from 0.05 A to 5 A (the 289 reads +2.3 mA at most, falling to -0.4 mA at 5 A). Other voltages were not tried. The supply's own current readback is steady and within spec from 0.4 A up (2.4 to 4.2 mA below the 289) but noisy at 0.25 A and below (single readings wander over 28 to 60 mA, the mean reads 6 to 9 mA low): for small currents use the 289 or average many samples. The output voltage under load includes the drop over the leads and any shunt. The tool cannot calibrate (no serial command for it); if the current is off, calibrate on the front panel, and do not change ISET to compensate. `iout_a` is the supply's own reading, a few mA below the real current from 0.4 A up; it is not ISET.
- Timing measured: the acknowledge arrives about 13 ms after a frame; a status reply takes 15 to 55 ms (median about 48 ms); the output follows a VSET step in about 0.2 s (0.9 s for 1 V down to 0.5 V); after ON the voltage stays near 11 mV for about 1.1 s (soft start) and is at the setpoint about 1.4 s after the command (1.7 s into a constant-current load), plus DELAY; OFF decays in about 0.3 s into a 10 MOhm meter (a battery or a big capacitor keeps the terminals up).
- Testing CC with an electronic load: put the e-load in constant-voltage mode at a voltage below VSET (or use a real resistor). Do NOT use the e-load's constant-resistance mode: its loop and the supply's CC loop fight, the current jumps between about 0 and 1.2 A every 0.5 to 2 s and the supply sits in CV most of the time. Lowering ISET and OCP together with current flowing sends ISET first and OCP after the current has come down (verified, no trip).
- Vout, Iout and Pout are refreshed every 100 ms by the supply and, by the firmware analysis, are frozen while its settings menu is open: a status taken then repeats old values. If the user says the supply shows a menu, ask them to leave it.

## Safety rules (never bypass)
The supply can damage what is connected. A protection trip sounds a loud alarm that only a front-panel key press clears, and a remote `on` switches the output on again even after a trip.

- Never trip a protection on purpose and never work around the refusals. The tool keeps OVP at least `max(0.2 V, 1.5 %)` above VSET (VSET = OVP = 3.00 V tripped on hardware), keeps a new OVP/OCP above what the terminals show now, OPP above the present power and OTP above the present temperature (5 W and 5 C margins), and sends protections and setpoints in an order chosen not to trip: raising VSET sends OVP first, lowering VSET and OVP together with the output on sends VSET first and OVP after the output has come down (verified, no trip). Give VSET and OVP (and ISET and OCP) in the same call. Keep OCP above ISET: at or above OCP for 100 ms the output trips, and in CC the current sits at ISET. With CV-first priority (`set --priority cv`) the switch-on current overshoots ISET briefly (measured about 60 % high, 0.81 A for ISET 0.5 A into a 3 V constant-voltage load; with CC first 0.54 A), so with CV first keep OCP well above ISET (not just above it), or leave the priority at CC first (the factory default; the serial setting is lost at power-off).
- Never raise the bench limits (`limits --max-voltage`, `--max-current`) or set OVP/OCP/OPP/OTP higher to get past a refusal without the user's explicit OK. Ask first. Never set the protections to zero or to the maximum to "turn them off".
- Ask before switching the output on or raising voltage or current, unless the user already asked for exactly that. Know what is connected (the limits' note, or ask). Start low: a new setup begins at a low VSET and a low ISET, and goes up in steps while you watch `status`.
- Ask before changing OVP/OCP/OPP/OTP, DELAY or REV on a supply that is on and in use, and before any command that is not an obvious part of what the user asked.
- If the output goes off without your command (`output_on` false after you switched it on, with no DELAY or REV set): assume a protection trip or a front-panel action (or a cut-off, on the Chinese screen: silent, no alarm sounds). Do not send `on` again. Tell the user; an alarm needs a human at the supply to press a front-panel key. Find the cause (OVP too close to VSET, a load pulling the current to OCP or OPP, temperature) before the next `on`.
- A supply with DELAY or REV set switches the output on later or toggles it. The supply cannot report them: `last_sent` shows them only if this tool sent them, so a front-panel DELAY or REV shows only as an output that comes on late or toggles. If the user did not ask for them, `set --delay 0 --rev 0`.
- `raw` is guarded: without `--unsafe`, documented registers go through the same checks as `set`, `on`, `list` and `color`, and undocumented registers are refused. Never add `--unsafe` on your own: the firmware acknowledges every valid frame and checks no ranges, so an out-of-range value is stored as sent and can reach the PWM setpoints unclamped (VSET, ISET), disable a protection (a very large OVP/OCP/OPP/OTP), trip one (0) or corrupt the EEPROM (a list index of 5 or more); an unknown id stores nothing but still makes the supply write its EEPROM. The MCP server has no raw tool.
- Do not kill a running `watch`, `log` or `sequence` with TaskStop or taskkill: use `openaxpp300s stop` (or `job_stop`) so the loop ends cleanly and a sequence switches the output off. If an agent session ends, check `openaxpp300s running` and `status`: a sequence or an output may still be active.
- Do not run the vendor PC app and this tool at the same time.

## EEPROM wear and the DATA box
Every valid frame, status queries included, makes the supply rewrite one EEPROM field: the one under its front-panel cursor (VSET by default after power-up on the Digital/Waveform screens). The firmware has no wear levelling and no compare (firmware analysis; the wear figures below are estimates). At 20 queries per second that is about 72 000 writes per hour to one cell; a typical EEPROM is rated about 1 million cycles. So:
- Poll slowly. The defaults are 1 s for `watch` and `log`; do not go below 1 s for anything long. Fast polling (0.1 s) is for short checks only.
- For a long log (hours), ask the user to select the DATA (CRL) box with the knob on the Digital/Waveform screen: with the cursor on DATA the firmware saves nothing to the EEPROM. (Turning the knob while DATA is selected clears the Ah/Wh/time statistics shown on the supply.) The tool prints an EEPROM warning when a planned run is long.
- Settings sent over serial survive a power cycle only if their field is the one under the cursor when a frame arrives (VSET by default; on the Chinese screen only for the selected list). OPP, OTP and CC-first persist only when the settings menu is left on the supply. The output state is never persisted. So after a power cycle, expect the supply to come up with its stored values (not what you sent) and the output off.

## The supply's menu and screens
- The supply has a settings menu, reached from the front panel. By the firmware analysis (not tried on hardware), entering it switches the output off once, freezes the measured values in the status reply and stops OPP/OTP checks, while a serial `on` still switches the output on. Do not use the tool while the menu is open; ask the user to leave it.
- The supply has a Digital screen, a Waveform screen and a Chinese screen. VSET, ISET, OVP, OCP, DELAY and REV act on the Digital and Waveform screens; the Chinese screen uses five parameter lists instead and cut-off current/time. The screen is chosen on the supply, not over serial, and the tool cannot read it. `NOT_APPLIED` after a VSET with the output on is the typical sign of the Chinese screen (verified: the supply ignored a Digital VSET there). The Chinese screen, its lists and its silent cut-offs are verified on hardware; see the parameter-list notes above.

## Errors and what to do
| code (exit) | meaning | do |
|---|---|---|
| `INVALID_ARG` (2) | bad option or a value outside the supply's range or grid (OPP in 10 W steps, OTP 60-100 in 10 C steps, whole seconds for DELAY/REV); also `--port` together with `--sim` | fix the command (`error.hint` gives the range) |
| `NOT_FOUND` (3) | no supply answered on any USB serial port, or the named port does not exist | ask the user to plug in the serial Type-C port and switch the supply on; `openaxpp300s ports --probe` lists what is there; give `--port COMx` |
| `BUSY` (4) | another program (the vendor PC app, a terminal) holds the port, or another openaxpp300s command held it longer than `--lock-wait` | close the vendor app; wait for the other command; `openaxpp300s running`; do not kill processes |
| `NOT_APPLIED` (5) | the supply acknowledged but the output did not follow: after a VSET with the output on it still reads another voltage after 3 s; or the output did not come down within 5 s, so a lowered OVP/OCP that had to wait for it was not sent; or a sequence step's output in CV is not at the step voltage (the sequence then switches the output off) | check the screen: the Chinese screen ignores the Digital registers; VSET may have been changed on the front panel; a battery or capacitor keeps the output up; read `status` before sending again. For `set`, the frames that went out are listed in `error.sent` |
| `NO_REPLY` (6) | no answer to a frame: wrong port, supply off, cable, or the supply in its bootloader | check power and cable, run `ports --probe`, retry once |
| `BAD_REPLY` (6) | an answer with a bad header, tail or checksum | retry once; noise or a wrong device on that port (`ports --probe`) |
| `PORT_ERROR` (6) | serial I/O error (cable pulled, driver error; one 'access denied' was seen on hardware) | the tool reopens the port and resends on its own (up to `--retries` times); if it persists replug the cable and check `status` before anything else |
| `UNSAFE_OPERATION` (7) | refused for safety, normally before anything was sent: above the bench limits, would trip a protection (OVP too close to VSET, OVP/OCP below the present output, OPP/OTP at the present power or temperature), an unknown register, or an unreadable limits file. Exceptions: when the output rises above the bench voltage limit after `on`, a list selection or during a sequence, the tool switches it off again and reports this code; `list set N ... --select` may have sent the list values before the selection is refused | read the message and hint; fix the values (for example `--ovp 5.5` with `-V 5`); never raise limits or add `--unsafe` on your own; ask the user |
| self-test failed (no error code: `"ok": false` with `failed` above 0, exit 1) | a check failed | read the failed `items[]` |

A `set` that fails after some of its frames went out lists them in `error.sent`; not every command does. After any failed change, do not assume nothing happened: read `status` first.

## Self-test
`openaxpp300s selftest` (MCP `selftest`) is read-only and never changes a setting. It checks, in order: S01 port resolved, S02 a valid status reply, S03 eight more replies valid, S04 reply latency (median 150 ms or less), S05 input voltage plausible (4.5 to 42 V), S06 temperature plausible (-10 to 95 C), S07 power equals voltage times current (within 0.05 W + 3 %), S08 output off reads below 0.2 V (skipped with the output on), S09 a bad-checksum frame is ignored and the next frame answered. About a second. Result: `passed`, `failed`, `complete`, `items[]` (`id`, `name`, `pass`, `measured`, `expected`, `skipped`). S01 and S02 failing is the port or the cable; S05 is the supply's input; S09 failing means the wrong device or a changed firmware. Run it whenever something looks off. It sends a few status frames, which count toward the EEPROM wear but are negligible.

## Try it without hardware
`openaxpp300s --sim <cmd>` (or env `OPENAXPP300S_SIM=1`) runs everything against a virtual PP300S: the firmware's frame parser, the acknowledge and reply timing, soft start, DELAY and REV, the protections and their latching alarm, the Digital and Chinese screens, a 10 MOhm voltmeter load, and an EEPROM write counter. The simulator wins over any port: with `--sim` the real supply is never touched, and `--port` together with `--sim` is `INVALID_ARG`. Its state is a JSON file shared between commands; control it with `python -m openaxpp300s.sim reset | show | set key=value ... | advance SECONDS | press | audit [--clear]` (`advance` moves its clock forward, `press` clears a latched alarm like a front-panel key, `audit` lists the frames it received, the last 500 writes). Use `--sim` to try a command line, a sequence file or a parser before touching the real supply, and set `OPENAXPP300S_HOME=<scratch folder>` so test files and state do not mix with real state. The simulator is not a measurement.
